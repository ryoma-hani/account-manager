# アカウント台帳

どのサービスに、どのIDで登録していて、パスワードをどこに保管しているかを一覧にする個人用Webアプリです。
パスワード本体は保管せず、パスワード管理アプリなどの保管場所を記録します。

## 現在の状態

ログイン、一覧・検索・絞り込み、登録・編集・削除、パス更新日の記録、選択肢の設定、ログインパスワード変更、サービス候補からの登録補助、携帯会社と電話番号の別管理、2段階認証の詳細登録を実装しています。一覧ではログインIDの隣にログインURLを表示して開けます。
ログイン前の「サンプルを見る」では架空のデータで操作できます。サンプルの変更はメモリ内だけに反映し、再読み込みでリセットされます。
Supabaseへの初期SQLの適用は完了し、台帳と個人設定の2テーブル、RLS、操作ごとのポリシー、更新日時のトリガーを作成済みです。GitHub Pagesへの初回公開も完了しています。以降は`main`へのpushで自動更新されます。
ログイン用ユーザーは1人作成済みで、メール確認済みです。一般向けの新規登録と匿名サインインは無効、Email認証は有効にしています。
点検判定などの単体テスト8件、ローカルPostgreSQL互換環境と実際のSupabaseでのアクセス制限テストは通過しています。実際のSupabaseでは、本人のCRUD、他人のデータへのアクセス拒否、所有者の偽装拒否、未認証のAPIアクセス拒否を確認しています。検証用データはROLLBACKで破棄しました。
PC・スマートフォンのブラウザ表示とサンプルの操作、APIモックでのログイン・保存・再読み込み・通信失敗時の表示も確認しています。実際の利用者による画面からのログイン・保存と、別ユーザーのログインセッションを使ったAPIアクセス確認は未完了です。
ログインパスワード変更欄は設定画面に追加済みです。実際のSupabaseアカウントでの変更操作は、本人が現在のパスワードを入力して行うため、開発時の確認では実行していません。
サイドメニューの開閉はPC・スマートフォン幅で、一覧・設定の表示、キーボード操作、閉じた際の表示幅と検索条件の維持を確認しています。
AIで改修するときは[AGENTS.md](./AGENTS.md)を参照してください。

## 採用する構成

- フロントエンド：Vue 3のCDN版グローバルビルド、vue3-sfc-loader、JavaScript ES Modules。
- UI：画面・共通部品を`.vue`に分割し、CSSは基本的に`css/style.css`に集約。
- データ：Supabase Database。
- 認証：Supabase Authのメールアドレス＋パスワード。DBはRLSで所有者ごとにアクセスを制限。
- 公開：GitHub Pages。フロントエンドのビルド工程は設けない。

vue3-sfc-loaderがブラウザ内でSFCをコンパイルします。初回読み込みにはその処理とCDNへの通信が必要です。
ライブラリのバージョンを固定し、更新時にVueとloaderの組み合わせを確認します。

## 初版の対象

添付されたExcelの構造を参考に、次の機能を実装しています。

- ログイン・ログアウト。
- 台帳の一覧、検索、カテゴリと保管場所での絞り込み。「見直しが必要」カードには、選択中の保管場所の要点検件数が表示されます。カードを押すと、その保管場所の要点検アカウントが表示されます。
- 一覧上部の「保管場所で絞り込み」から保管場所または「保管場所未設定」を選べます。中央のカードには選んだ保管場所名と登録件数が表示されます。「見直しが必要」で絞ったあとに中央のカードを押すと、選んだ保管場所の一覧に戻ります。「登録アカウント」を押すと、すべての絞り込みが解除されます。カテゴリや検索を組み合わせた結果の件数は一覧に表示されます。
- アカウント情報の登録・編集・削除。
- 一覧にログインURLとスマホアプリ対応の有無を表示します。「利用方法で絞り込み」で「Web（URLあり）」「スマホアプリ対応」「アプリのみ（URLなし）」を選べます。URLとアプリの両方があるサービスは、Webとスマホアプリ対応のどちらにも表示されます。
- 新規登録時にサービス候補を検索・選択し、サービス名とログインURLを自動入力する機能。候補にはブランドカラー付きロゴを表示します。Googleは公式の4色Gマーク、AmazonはAmazon.co.jp公式サイトのアイコンを使い、その他はSimple Iconsのブランドカラーを使います。ロゴがない・読み込めない場合はサービス名の頭文字を表示します。ロゴ自体が単色のブランドはその色で表示されます。候補にないサービスは「その他」から手入力できます。候補一覧と任意のロゴIDは`js/config/site-catalog.js`で管理し、追加の希望に応じて更新します。
- ログインURLを開く操作。
- 新規登録では、サービス候補を選ぶか、候補一覧にあるサービス名やURLのドメインを入力すると、おすすめのカテゴリが入ります。既存の未分類アカウントでは編集画面で候補を確認し、保存すると反映されます。候補は変更でき、分類済みのカテゴリはそのまま表示します。判定できない場合やおすすめのカテゴリが設定の選択肢にない場合は未分類になります。
- 一覧の保管場所からBitwardenのWeb保管庫またはこのMacにインストールされたBitwardenアプリを開けます。ノートン パスワード マネージャーにはWeb版へのリンクがあります。Webリンクは新しいタブで開きます。「サンプルを見る」から、Figma行のノートンとAmazon行のBitwardenのリンクを試せます。
- 点検状況の自動判定とパス更新日の記録。
- 設定画面での選択肢の管理。
- 設定画面でのログインパスワード変更。現在のパスワードによる本人確認と、新しいパスワードの確認入力を行います。Supabase Authで更新し、サンプルモードでは利用できません。
- 台帳のログインを守る2段階認証。認証アプリを登録すると、メールアドレスとパスワードに続けて6桁の確認コードが必要になります。
- ワークスペースの「電話番号」画面で、携帯会社と電話番号を複数登録・編集・削除する機能。アカウント追加フォームとは分け、個人設定のJSON内に保存します。国内電話番号を入力し、本人の設定行に対するRLSで保護します。サンプルモードでは変更はメモリ内だけです。
- 保管先での項目名は登録・編集フォーム、一覧、検索対象から削除しました。既存値は保存データの互換性のため保持し、画面には表示しません。新しい登録では使いません。
- アカウント追加・編集時、2段階認証をSMSにすると登録済み電話番号を選べます。認証アプリの場合は候補から選ぶか、アプリ名を手入力できます。一覧にも詳細を表示します。2段階認証の種類と詳細は既存の`accounts.two_factor`欄にまとめて保存するため、テーブル変更は不要です。
- PCとスマートフォンで使える画面。
- 一覧・設定の画面上部にあるボタンでのサイドメニューの開閉。閉じると本文を広く表示でき、同じボタンで再表示できます。

「スマホアプリで利用できる」はアカウントの追加・編集画面で設定します。アプリ専用サービスはログインURLを空欄にします。登録済みのログインURLは保持され、アプリ対応は必要に応じて各アカウントで設定できます。「アプリで開く」は、対象のスマホで起動を確認した公式リンクを登録した場合だけ表示します。現時点でアプリを直接開く公式リンクは未登録です。

「はま寿司」には、iPhoneで設定したショートカットを使う「ショートカットで開く」があります。はま寿司アプリを入れたiPhoneで、「ショートカット」アプリに「アプリを開く」→「はま寿司」のアクションを作り、`OpenHamaSushi` と名前を付けます。「サンプルを見る」で「はま寿司」を検索すると、はまナビのログインURLと一緒に試せます。自分の台帳でも、サービス名を「はま寿司」にして「スマホアプリで利用できる」にチェックを入れると使えます。

Excelのインポート・エクスポートは初版では前提にせず、必要になった段階で追加します。

### 台帳ログインの2段階認証を設定する

1. Macで台帳にログインし、「設定」→「台帳のログインを守る2段階認証」→「2段階認証を設定する」を開きます。
2. iPhoneのカメラでQRコードを読み取り、標準の「パスワード」アプリに登録します。Google Authenticatorなどを使う場合は、認証アプリ内のQRコード読み取りを使います。同じ端末で設定する場合は、設定キーを表示して手入力できます。
3. 認証アプリに表示された6桁の確認コードを台帳に入力し、「確認して有効にする」を押します。次回のログインから確認コードが必要です。

認証アプリの登録を解除するには、2段階認証を済ませた状態で「設定」の「登録を解除」を使います。端末を紛失するなどして確認コードを使えなくなった場合は、Supabaseプロジェクトの管理者にご確認ください。設定用のQRコードと設定キーは、認証アプリへの登録にだけ使ってください。

### 台帳の項目

| 項目 | 扱い |
| --- | --- |
| サービス名 | 登録先の名前 |
| ログインURL | ログイン画面のURL |
| スマホアプリで利用できる | 対応するサービスにチェック。「スマホアプリ対応」と「アプリのみ」の絞り込みに使う |
| 開く | URLから表示するリンク |
| ログインID | 登録先で使うID。長いIDは列の中で折り返し、横のボタンで全文をコピーできます |
| 登録メールアドレス | 登録に使ったメールアドレス |
| 保管場所 | パスワード管理アプリなど。Bitwardenは一覧からWeb保管庫とアプリを、ノートン パスワード マネージャーは公式Webページを開けます |
| パスキーの保管先 | パスキーを保存したアプリ名。設定で選択肢を変更できます。登録すると一覧の2段階認証欄に併記され、SMSの有無と独立して編集できます |
| 2段階認証 | 利用する認証方法。SMSは選んだ電話番号、認証アプリはアプリ名も記録 |
| カテゴリ | サービスの分類。一覧ではログインURLと保管場所の間に表示 |
| 状態 | 利用状況。登録・編集で確認・変更できる |
| 更新日 | 情報を更新した日 |
| パス更新日 | パスワードの更新日として手動で記録する日。従来の「最終点検日」と同じ欄 |
| メモ | パスワードや認証コードを含めない補足 |
| 要点検 | 次のルールから自動で表示 |

### 点検ルール

Excelの判定順を引き継ぎ、最初に該当した結果を表示します。
サービス名が空の行には判定結果を表示しません。

1. 2段階認証が「なし」なら「2FAなし」。
2. 保管場所が空なら「保管場所未設定」。
3. パス更新日が空なら「未点検」。
4. パス更新日から90日を超えていたら「90日超未点検」。
5. それ以外は「OK」。

この「OK」は上記の点検項目の判定結果です。

| 項目 | 選択肢 |
| --- | --- |
| 保管場所 | 1Password、iCloudキーチェーン、Bitwarden、ノートン パスワード マネージャー、ブラウザ(Chrome等)、紙のノート、その他 |

## Supabaseの準備

引き継ぎを簡単にするため、友人が所有・管理するSupabaseアカウントでプロジェクトを作ることを推奨します。

1. Supabaseに登録し、プロジェクトを作成します。Securityは「Enable Data API」をON、「Automatically expose new tables」をOFFにします。「Enable automatic RLS」はOFFでも動作します。
2. プロジェクトのConnect画面から、Project URLとPublishable key（`sb_publishable_...`）を確認し、`js/config/supabase.js`に設定します。
3. Authentication → Users → Add user → Create new userで利用者を作成します。メールアドレスとログインパスワードを設定し、Auto confirm userをONにします。ログインパスワードは利用者自身で管理します。
4. Authentication → Sign In / Providersで一般向けの新規登録と匿名サインインを無効にします。Email認証は有効にします。
5. SupabaseのSQL EditorでNew queryを開き、[supabase/schema.sql](./supabase/schema.sql)の全文を貼り付けてRunを押します。このSQLがテーブル、RLS、APIアクセス権限、更新日時のトリガーを作成します。同じ内容は再実行できます。
6. [supabase/verify-access.sql](./supabase/verify-access.sql)を別のクエリで実行し、最後に`PASS`が返ることを確認します。テスト用の2人と台帳データはトランザクション内だけで使い、ROLLBACKで破棄します。途中でエラーになった場合も`ROLLBACK;`を実行してください。
7. SQL Editorで [supabase/enable-ledger-mfa.sql](./supabase/enable-ledger-mfa.sql) を実行し、認証アプリの登録を済ませた利用者の台帳と個人設定に確認コードを要求します。Supabase Authで認証アプリによる登録と確認を有効にしてください。続けて [supabase/verify-mfa.sql](./supabase/verify-mfa.sql) を実行し、最後に `PASS` が返ることを確認します。
8. SQL Editorで [supabase/add-mobile-app-availability.sql](./supabase/add-mobile-app-availability.sql) を実行し、スマホアプリ対応の記録欄を追加します。既存のプロジェクトでも、このSQLを適用してからアプリを更新します。
9. 既存のプロジェクトでは [supabase/add-passkey-location.sql](./supabase/add-passkey-location.sql) を適用してパスキーの保管先を追加します。既存のアカウントの初期値は空欄です。
10. アプリから手順3の利用者でログインし、架空のアカウントを登録・編集して、再読み込み後も残ることを確認します。

`schema.sql`は初期セットアップ用です。既存の台帳データを削除しません。今後テーブルの構造を変更するときは、既存データを保つ変更用SQLを追加してください。

Project URLとPublishable keyはブラウザで公開するための情報です。
Secret key、service_role key、DBのパスワード、利用者のログインパスワードは共有・コミットしません。

### なぜ.envではなくconfigのJSに書くのか

このアプリにはビルド工程がなく、ブラウザは`.env`を自動では読み込みません。そのため、公開できる接続情報を`js/config/supabase.js`にまとめています。
Viteの`VITE_...`もビルド時にフロントエンドのJSに含まれる公開情報です。`.env`に置くこと自体は、ブラウザへ渡す値を秘密にする仕組みではありません。
保存データへのアクセスはSupabase AuthとRLSで制御します。

認証のSite URLと必要なRedirect URLsは、公開URLに合わせて設定します。
ローカル確認先は`http://localhost:8000/`です。
公開先は[https://ryoma-hani.github.io/account-manager/](https://ryoma-hani.github.io/account-manager/)です。

Authentication → URL Configurationで、Site URLに予定する公開URLを設定し、Redirect URLsにローカルURLと公開URLを追加します。

### DBの構成

| テーブル | 内容 |
| --- | --- |
| `accounts` | 台帳。所有者の`user_id`とアカウント情報を保存 |
| `user_settings` | 利用者ごとの選択肢。`user_id`ごとに1行 |

携帯会社と電話番号も`user_settings.options`内に保存します。既存テーブルを使うため、電話番号機能の追加に伴うSQL変更はありません。

「開く」と「要点検」は画面で生成し、DBには保存しません。情報の更新日はDB側のトリガーで自動更新します。

## 開発時の起動方法

プロジェクトのルートで実行します。

```sh
python3 -m http.server 8000
```

`http://localhost:8000/`を開きます。`file://`では起動しません。

8000番で別のアプリが起動している場合は、そのアプリを止めずに別のポートを使います。
今回のローカル確認では8001番を使っています。

```sh
python3 -m http.server 8001 --bind 127.0.0.1
```

この場合は`http://localhost:8001/`を開きます。`/login`など別アプリのURLを使わず、画面のタイトルが「アカウント台帳」であることを確認してください。

単体テストはNode.jsがある環境で、次のコマンドで実行できます。npmのインストール作業は不要です。

```sh
node --test tests/ledger.test.mjs
```

## 公開と引き継ぎ

引き継ぎ先の利用者にGitの知識がないことを前提に、AIが動作確認後のcommit・pushまで担当します。通常は意味のある作業単位で適宜自動実行し、`main`へのpush後に公開用Actionsと公開URLを確認します。利用者が「まだpushしない」などと明示した場合は、その指示を優先します。詳しい進め方は[AGENTS.md](./AGENTS.md)に記載しています。

GitHub Pagesの無料プランでは公開リポジトリを使います。公開されるHTML、JS、SFCに実際の台帳や秘密情報を含めず、実データはSupabaseへ保存します。
公開前に未ログイン・別ユーザーからのAPIアクセス制限と、本人の登録・編集・削除を確認します。

1. GitHubのリポジトリでSettings → Pagesを開き、SourceをGitHub Actionsに設定します。
2. 完成したソースを`main`へpushします。
3. Actionsの「Deploy GitHub Pages」が成功し、Pagesに表示されるURLで起動できることを確認します。

ワークフローは公開に必要な`index.html`、`favicon.svg`、`.nojekyll`、`css/`、`js/`だけをコピーして配信します。フロントエンドのコンパイルは行いません。
SQL、開発資料、テストはPagesの配信対象に含めません。

改修箇所は、画面が`js/pages/`、共通UIが`js/components/`、API通信が`js/services/`、点検ルールなどが`js/utils/`、配色・レイアウトが`css/style.css`です。
引き継ぎ時は、GitHubとSupabaseの管理アカウント、ログイン用のメールアドレス・パスワードの保管先、公開URLを本人が把握できる状態にしてください。
